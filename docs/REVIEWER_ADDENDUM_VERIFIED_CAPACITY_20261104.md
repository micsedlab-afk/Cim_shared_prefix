# Reviewer addendum: source-verified system opportunity and strict evidence limits

**Date:** 4 November 2026. **Authoritative source:** [VERIFIED_CAPACITY_GPU_TRAFFIC_BOUNDS_20261104.md](VERIFIED_CAPACITY_GPU_TRAFFIC_BOUNDS_20261104.md). **Reproduced** in [GitHub CI 41917353115](https://github.com/micsedlab-afk/Cim_shared_prefix/actions/runs/41917353115) with 10 source-only unit/property tests, 136 macro-budget/prefix cases, 34 ideal fused GPU HBM/L2 necessary-rate cases and 14 native Llama/Mistral/OPT macro-geometry cases.

This addendum supersedes any inference that hypothetical `0.5mm² / 256 ports / 16TB/s V / 64TMAC/s` parameter settings establish a practical system-level advantage. The previous parameter-sweep artifacts remain reproducible *conditional analyses*; they do not provide implementation evidence.

## Reviewer objection → independently grounded answer

| Issue | Qualified result | Qualification / response |

| Does the accelerator fit? | One native Llama P2048 layer requires **14.256324mm²** of *complete* signed-K4 CIM and FP16-V SRAM macro area. Two signed K layers **alone** already require 26.2144mm². At 16mm², at most one complete layer; K+V P2304 requires 16.038mm²/layer and fits none. | **Necessary physical capacity**, with no periphery/clock/buffers included. Not a fabricated implementation. |
| Can scheduling recover the missing capacity? | Arbitrary **permanently resident** 16-token-layer tiles can fit at most 143 in 16mm², out of 4096 tiles required at P2048 (3.491%). Complete-first packing (128+15) minimizes the number of touched layers for any strictly positive per-layer setup cost; exhaustive small-case property tests passed. | Exact for the specified tile/macro organization and persistent residency; moving/reprogramming the tiles every output token is a different schedule requiring extra time. |
| Is there a region with full-model residency and reduced score transfer? | At 16mm², all 32 K+V layers fit only for P≤64 (16-token alignment). But the context+LSE endpoint sends **8320B/layer/token**, versus **8192B** of FP32 completed scores at P64. Reduction requires P>65, where complete 32-layer K+V residency is impossible. | Strict mathematical incompatibility for this model geometry and output formats. |
| Are GPU comparisons strong and fair? | Source A100 80GB SXM HBM2e published **2039 GB/s**, nominal L2 **40MB**, FP16 dense peak **312TFLOPS**. An *ideal fused* source model that never materializes score tensors and reads K and V exactly once gives P2048 B1 necessary floors **4.114079µs HBM** and **1.161986µs source L2**. | Both are theoretical lower floors, not actual GPU timings or achieved Hydragen. The L2 bandwidth used comes from the LLMCompass model, not measured A100. |
| How much full-decoder opportunity exists? | In a **B1 FP16 model with each dense matmul weight streamed once per generated token**, weights + LM head total **15,009,316,864B**, full prefix KV P2048 adds **268,435,456B**. ## What is publishable from these facts

The paper can report the complete-macro area/tile accounting, the exact storage incompatibility, optimistic cache-residency limits, native pinned model geometry, derived GPU source roofs, necessary digital thresholds, and archival numerical-quality evidence. Those are transparent and reproducible.

It **cannot currently claim** hardware speedup, near-memory integration feasibility, an advantageous energy figure, a superior Hydragen implementation, a 7-nm digital MAC physical area, or greater-than-baseline end-to-end tokens/s.

This is a scientifically meaningful negative/feasibility result. A positive system-level accelerator contribution requires substantially more source-supported evidence or a different area/technology/workload balance. No favorable GPU or SRAM bandwidth has been introduced by assumption.
